# 项目初始化 Skill

## 目标

把一个想法初始化为可运行、可验证、可继续迭代的独立开发项目。初始化的结果不是一套堆满依赖的脚手架，而是：

- 技术边界和关键取舍有文档记录；
- 本地开发环境可以启动；
- 至少有一个可执行、可验证的 Hello World 链路；
- 后续工作可以按计划推进，文档反映当前真实状态。

## 使用前提

仅在初始化新项目或补建项目骨架时使用本流程。文档读取时机、规则职责与文档维护方式以 [技能入口](../SKILL.md) 为准；已有项目沿用其协作约定和实现，不重新套用整套初始化流程。

## 默认技术栈

只有在没有现有技术约束时，才使用以下默认方案。若现有项目已经采用其他方案，记录差异和原因，不为统一技术栈进行无关迁移。

### Monorepo

需要多个应用或共享包时，默认使用 `pnpm workspaces` 管理 Monorepo；单一应用可使用普通项目结构。以下是按需选取的目录示例：

```text
.
├── apps/
│   ├── server/              # Node.js + Hono
│   ├── admin/               # Next.js 管理后台，按需创建
│   ├── mobile/              # Expo 移动端，按需创建
│   └── miniapp/             # uni-app 小程序，按需创建
├── packages/
│   ├── db/                  # Prisma schema、迁移和数据库访问
│   ├── config/              # 共享 TypeScript、ESLint 等配置，按需创建
│   └── types/               # 跨应用共享类型，按需创建
├── package.json
├── pnpm-workspace.yaml
└── docs/
    ├── architecture.md
    └── plan.md
```

实际项目仍应根据需求删减目录。不要为了保持目录“完整”而创建不使用的应用或共享包。默认不引入 Turborepo、Nx 等任务编排工具；当构建、测试或缓存时间已经成为明显瓶颈时，再评估引入。

| 模块 | 默认方案 | 适用范围 |
| --- | --- | --- |
| 后端 API | Node.js + Hono | 轻量 HTTP API、鉴权和业务编排 |
| 数据访问 | Prisma | PostgreSQL schema、迁移和类型安全查询 |
| 数据库 | PostgreSQL | 业务主数据和事务性数据 |
| 缓存 | Redis | 只有出现明确的性能、队列或临时状态需求时引入 |
| 管理后台 | Next.js + shadcn/ui + Tailwind CSS | 内部运营、审核和数据管理 |
| 移动端 | Expo | 需要原生能力或独立移动应用时使用 |
| 小程序 | uni-app | 需要微信或多端小程序交付时使用 |

不要为了“未来可能需要”预先创建所有客户端、Redis、微服务或复杂权限系统。先验证核心用户流程。

### 微信小程序导航栏

仅适用于微信小程序：所有页面都不要实现右上角的 `•••` / `◎` 胶囊按钮（menu-pill）。这是微信客户端自带的系统胶囊，由微信渲染在原生层。设计稿里画出它只是为了还原真机效果，不是需要实现的 UI；自己实现会和系统胶囊重叠。自定义导航栏（`navigationStyle: custom`）只做返回按钮和标题，右侧留空。

后续页面开发也应遵守这条约束。需要将其写入目标项目 `AGENTS.md` 时，按技能入口的规则同步约定处理，避免覆盖或重复添加已有规则。

## 初始化流程

### 1. 盘点上下文

确认以下信息；无法确认时采用最小可行假设，并写入 `docs/plan.md`：

- 产品服务谁，以及当前要验证的核心问题；
- 首个可交付用户流程和明确的成功标准；
- 目标平台：Web、管理后台、移动端或小程序；
- 当前目录结构、包管理器、运行时版本和已有服务；
- 必需的外部服务、凭据、环境变量和本地依赖。

### 2. 固化项目文档

在项目的 `docs/` 目录创建或更新：

- `docs/plan.md`：当前目标、按需选取的迭代、每个迭代的任务和验收标准；
- `docs/architecture.md`：模块边界、数据流、技术选型、运行方式、环境变量和已知限制。

已有同类文档时沿用其命名和结构。文档应描述当前真实状态，不记录尚未实现的能力为“已完成”。对影响交付或维护成本的技术选型，简要说明选择理由；仅在有实际取舍时记录替代方案和引入条件。

### 3. 设计最小模块边界

先按业务边界划分模块，而不是按未来团队规模拆分服务。明确：

- API 入口、路由和错误响应约定；
- 数据模型、迁移方式和种子数据；
- 前端或客户端调用 API 的方式；
- Monorepo 中各应用与共享包的依赖方向；
- 配置与密钥的来源；
- 日志、健康检查和本地启动命令。

使用 Monorepo 时，应用之间通过 `packages/*` 共享稳定的类型、数据库访问和配置，避免直接引用彼此的内部实现。只有在部署、权限或运行时确实不同，并且拆分能立刻降低复杂度时，才拆成多个应用或服务。

### 4. 初始化可运行骨架

按项目实际需求完成最小骨架：

1. 按选定结构初始化 `package.json` 和 TypeScript 配置；仅在使用 workspaces 时创建 `pnpm-workspace.yaml`。
2. 需要独立后端时，在 `apps/server` 创建后端服务、健康检查接口和统一启动命令。静态页面、纯客户端或已有框架内置 API 能满足需求时，无需额外服务。
3. 需要关系型持久化时再接入 Prisma 与 PostgreSQL，创建第一版 schema 和迁移；Monorepo 可放在 `packages/db`。无需持久化时不安装数据库依赖。
4. 创建实际需要的客户端或管理后台；Monorepo 放在 `apps/`，单应用沿用其框架结构；不需要的端不创建。
5. 需要环境变量时，提供根目录 `.env.example` 或按应用提供模板，只包含变量名、用途和示例格式，不写入真实密钥。
6. 为实际存在的应用提供可执行的开发、构建和相关验证命令；不要创建占位测试或无用的迁移命令。使用 workspaces 时优先通过 `pnpm --filter <workspace>` 精确执行。

### 5. 完成 Hello World 验证

Hello World 必须是可执行的链路，而不是只打印一行文字：

- 目标应用能按架构文档启动，相关根目录或 workspace 脚本可以执行；
- 有后端时，健康检查或最小业务 API 返回预期结果，客户端或命令行能访问它；
- 无后端时，实际打开目标页面或运行入口，验证最小交互或输出；
- 验证当前链路涉及的成功、失败和缺失配置行为，不为测试引入无关基础设施。

如果当前链路需要 PostgreSQL 但尚未可用，先验证不依赖数据库的可运行部分，并在文档中标记数据库联调为阻塞项；不要伪造已完成的联调结果。

### 6. 按需划分迭代

默认参考以下五个阶段，将计划控制在五个迭代内；按项目规模合并或省略无关阶段，不为凑数增加任务。每个选用的迭代都必须有一个可演示或可验证的结果：

1. **基础可运行**：项目骨架、配置、健康检查、开发命令和最小页面。
2. **核心闭环**：最重要的数据模型、API 和用户主流程。
3. **可用性**：错误处理、加载和空状态、基础权限、数据校验和关键测试。
4. **发布准备**：部署配置、生产环境变量、日志、备份或恢复方案，以及真实环境验收。
5. **反馈迭代**：根据用户反馈修复最高价值问题；只有数据证明需要时才扩展性能和基础设施。

每个迭代写清楚：目标、范围、不做什么、验收条件、依赖和风险。任务按优先级排序，优先能带来用户反馈或收入验证的工作。

### 7. 联调、测试和验收

按照`architecture`启动依赖，执行由风险决定的最小测试集：

- 静态检查和构建；
- API 健康检查；
- 核心 API 的成功和失败路径；
- 前后端联调的核心用户流程；
- 数据库迁移和必要的种子数据验证。

记录执行过的命令、结果、未执行项目及原因。测试失败时先修复阻塞核心流程的问题，再考虑非关键优化。

### 8. 回写工作记录

按 [技能入口的文档维护规则](../SKILL.md#文档维护) 同步初始化结果，使计划状态和架构事实与本次实际交付一致。

## 完成标准

只有满足以下条件，才可以把初始化标记为完成：

- `docs/plan.md` 已有与项目规模相称的迭代、验收标准和明确的下一步；
- `docs/architecture.md` 与当前代码一致；
- 新成员或未来的自己能按文档启动项目；
- Hello World 链路已实际验证，结果已记录；
- 必要的检查通过，剩余问题已标注为风险或阻塞项；
- 没有提交真实密钥、无关依赖或未使用的服务。

## 输出格式

完成任务后，用简短摘要说明：

1. 改动了哪些文件；
2. 采用了哪些关键取舍；
3. 执行了哪些验证及结果；
4. 当前阻塞项和下一步是什么。
